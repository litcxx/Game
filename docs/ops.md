# Эксплуатация: игра на VPS

Как поднять игру на своём сервере с публичной ссылкой `https://<домен>/`, выкладывать новые версии, откатываться и смотреть логи. Всё делается тремя скриптами из `deploy/`. Инструкцию целиком проверяет `deploy/rehearse.sh` (см. [Репетиция](#репетиция)).

```
браузер ──https──► Caddy :443 ──► /opt/territory/current/client   (страница и ассеты)
        ──wss /ws─►            └─► 127.0.0.1:27998                (игровой сервер, systemd: territory)
```

- **Caddy** получает и продлевает сертификат Let's Encrypt сам. Он раздаёт клиент как статику и проксирует `/ws` на игровой сервер.
- **Игровой сервер** слушает только `127.0.0.1`: снаружи до него не достучаться, только через Caddy. Он работает как systemd-сервис `territory`: после любого завершения, включая `kill -9`, поднимается через 1 с.
- **Выкладка** (release) — это папка `/opt/territory/releases/<время>-<коммит>` с сервером, его конфигом и собранным клиентом. Ссылка `/opt/territory/current` указывает на текущую выкладку. Хранятся три последние, откат — одна команда.

## Что нужно

- **VPS** с Ubuntu 24.04 LTS (amd64 или arm64):
  - от 2 vCPU и 2 ГБ памяти (сборка на месте; при памяти меньше 3 ГБ `setup.sh` сам добавит 2 ГБ swap);
  - от 20 ГБ диска;
  - публичный IPv4.
  
  Регион — ближе к большинству игроков. Компенсации лага нет, и от RTT зависит, получится ли увернуться от снаряда (ГДД, вопрос 16.17).
- **Домен.** Let's Encrypt не выдаёт сертификаты на голый IP. A-запись (и AAAA, если у VPS есть IPv6) должна указывать на VPS. Подойдёт и бесплатный поддомен, например DuckDNS.
- **Открытые порты 80 и 443.** По 80 Let's Encrypt проверяет владение доменом, 443 — сама игра.
- **Пользователь с `sudo`** на VPS. Скрипты запускаются от него, не от root: `deploy.sh` сам попросит `sudo` для установки.

## 1. Домен

Создайте у регистратора (или в DuckDNS) A-запись `game.example.ru → <IP VPS>` и проверьте:

```bash
dig +short game.example.ru     # должен вернуть IP VPS
```

Пока запись не разошлась, Caddy не получит сертификат. Он будет повторять попытки сам.

## 2. Подготовка VPS (один раз)

```bash
ssh you@<IP VPS>
git clone https://github.com/litcxx/Game.git && cd Game
sudo deploy/setup.sh game.example.ru
```

Если репозиторий приватный, клонируйте по HTTPS с токеном GitHub (fine-grained, только чтение этого репозитория) или по SSH с deploy key.

Что делает `setup.sh` (15–20 минут, почти всё время уходит на сборку protobuf):

1. Ставит пакеты для сборки: `g++`, `cmake`, `ninja`, Boost, OpenSSL, `git`, `jq`.
2. При памяти меньше 3 ГБ без swap добавляет 2 ГБ swap в `/swapfile`.
3. Собирает protobuf 36.2 из исходников тем же скриптом, что и CI (`server/scripts/install-protobuf.sh`), в `/usr/local`.
4. Ставит Node.js 22 (архив с nodejs.org, проверка SHA-256) в `/usr/local/lib/nodejs`.
5. Ставит Caddy (`.deb` из релизов Caddy на GitHub, проверка SHA-512). Он приходит со своим systemd-сервисом `caddy`.
6. Создаёт системного пользователя `territory` без входа и без домашней папки и папку `/opt/territory`.
7. Ставит сервис `/etc/systemd/system/territory.service` (из `deploy/territory.service`) и включает автозапуск при загрузке.
8. Ставит сайт `/etc/caddy/Caddyfile` (из `deploy/Caddyfile`, с вашим доменом) и перезагружает Caddy.

Запускать повторно безопасно: уже поставленное пропускается, а сервис и сайт обновляются, только если их файлы в репозитории изменились. Так же обновляются версии: поменяйте версию и хэш в `setup.sh` (Node, Caddy) или в `install-protobuf.sh` и запустите `setup.sh` снова.

## 3. Выкладка

Первая и каждая следующая, из того же клона:

```bash
cd ~/Game && git pull && deploy/deploy.sh
```

Что делает `deploy.sh` (2–5 минут):

1. Собирает сервер (пресет `release`) и прогоняет его unit-тесты. Если тесты падают, выкладка останавливается, а старая версия продолжает работать.
2. Собирает клиент (`npm ci`, `npm run build`). Собранная страница подключается к `wss://<свой домен>/ws`.
3. Складывает выкладку в `/opt/territory/releases/<время>-<коммит>`:
   - `bin/server`;
   - `config.json` — это `server/config/config.json` с `server.ip = 127.0.0.1`; правила игры берутся из репозитория;
   - `client/`.
4. Переключает `/opt/territory/current` на новую выкладку одной операцией и перезапускает сервис. Сервер должен начать принимать соединения за 10 с.
5. Проверяет, что игрок может войти: `client/scripts/smoke.ts` против `127.0.0.1`.
6. Удаляет выкладки старше трёх последних.

**Выкладка начинает новый мир.** Пока мир не сохраняется (GAME-019), перезапуск сервера сбрасывает территорию и персонажей. Игроки видят «Переподключение…» и через пару секунд возвращаются сами, уже новыми персонажами под своими никами. Выкладывайте между сессиями игры.

Страница отдаётся с `Cache-Control: no-cache`, поэтому после выкладки обычная перезагрузка вкладки получает новый клиент. Ассеты (`/assets/*`) кэшируются навсегда: их имена меняются вместе с содержимым. Если изменился протокол, вкладка со старым клиентом получит `PROTOCOL_VERSION` и кнопку «Перезагрузить».

## 4. Проверка

На VPS:

```bash
deploy/check.sh game.example.ru
```

```
ok   territory and caddy are running
ok   https://game.example.ru/ serves the game
ok   wss://game.example.ru/ws takes the game's WebSocket
ok   kill -9: back in 1210 ms (pid 4127 -> 4163)
```

`check.sh` действительно убивает сервер через `kill -9`, поэтому текущий мир сбрасывается.

Снаружи:

- откройте `https://game.example.ru/` с телефона через мобильный интернет, не через Wi-Fi рядом с VPS;
- с машины разработчика прогоните smoke по публичному адресу (оставляет в мире пару персонажей на 30 с):

```bash
cd client
SERVER_URL=wss://game.example.ru/ws npx tsx scripts/smoke.ts
SERVER_URL=wss://game.example.ru/ws npx tsx scripts/reconnect_smoke.ts
```

## 5. Откат

```bash
deploy/deploy.sh rollback     # на выкладку перед текущей
```

Откат ничего не собирает: он переключает `current` на предыдущую выкладку и перезапускает сервис. Это занимает секунды. Повторный запуск откатывает ещё на одну выкладку назад, пока они есть (хранятся три). Какая выкладка сейчас работает:

```bash
readlink /opt/territory/current
ls /opt/territory/releases
```

## 6. Логи и метрики

Сервер пишет в журнал systemd:

```bash
journalctl -u territory -f                    # в реальном времени
journalctl -u territory --since "1 hour ago"
journalctl -u territory -n 50                 # почему не поднялся
journalctl -u caddy -f                        # сертификаты, прокси
```

Раз в минуту сервер пишет строку `metrics {...}`: CCU, время тика, размер снапшотов, ошибки по кодам. Поля описаны в [server/README.md](../server/README.md#logs--metrics). Выгрузка за плейтест:

```bash
journalctl -u territory -o cat --since "2 hours ago" \
  | sed -nE 's/^\[([^]]+)\] \[info\] metrics \{/{"time":"\1",/p' > metrics.jsonl
```

Дальше это превращается в CSV или отвечает на вопросы через `jq`, как описано там же.

Для плейтеста всё это собирает одна команда: лог окна, метрики и сводка для отчёта (сеть, сервер, игра, время каждого игрока в мире). Подробнее — в [playtests/pt-0.md](playtests/pt-0.md):

```bash
deploy/playtest-report.sh "2026-10-02 18:55" "2026-10-02 19:40"
```

Уровень логов и интервал метрик задаются в секции `log` файла `server/config/config.json`. Изменения вступают в силу со следующей выкладкой.

## 7. Сервис

```bash
systemctl status territory
sudo systemctl restart territory    # новый мир, игроки переподключатся
sudo systemctl stop territory       # до start или до перезагрузки VPS
```

Остановка отправляет SIGTERM: сервер говорит всем `SERVER_SHUTDOWN` и корректно закрывается (на это даётся 15 с). После падения или `kill -9` systemd поднимает его через 1 с, без ограничения числа перезапусков.

## 8. Безопасность

- Снаружи открыты только ssh, 80 и 443. Игровой порт 27998 слушается на `127.0.0.1`.
- Сервер работает от `territory` без прав, в песочнице systemd: без capabilities, с файловой системой только для чтения, с фильтром системных вызовов. Писать на диск ему нечего, логи уходят в журнал. Оценка `systemd-analyze security territory` — 1.1 из 10 (OK).
- Файрвол — рекомендуется, но скрипты его не включают: легко закрыть себе ssh. Если ssh на стандартном порту 22:

  ```bash
  sudo ufw allow OpenSSH && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw enable
  ```

  У многих провайдеров есть и свой файрвол в панели.
- Обновления безопасности Ubuntu ставятся сами (`unattended-upgrades` включён по умолчанию). Caddy, Node и protobuf закреплены в скриптах и обновляются вручную, см. раздел 2.

## Репетиция

`deploy/rehearse.sh` проходит эту инструкцию целиком в Docker-контейнере с systemd на чистой Ubuntu 24.04. Вместо домена там `localhost`, и вместо Let's Encrypt сертификат выдаёт собственный CA Caddy. Проверяются:

- `setup.sh` и `deploy.sh` на чистой машине;
- страница по https и заголовки кэша;
- вход и resume по `wss` через Caddy;
- что сервер слушает только `127.0.0.1`;
- `check.sh` (`kill -9`);
- выкладка при игроке в сети: он возвращается сам;
- хранение трёх выкладок, откат и повторный `setup.sh`.

```bash
deploy/rehearse.sh        # 20–30 минут, в конце REHEARSAL: PASS
```

Запускайте после любых изменений в `deploy/`. Нужен Linux с Docker, который умеет запускать привилегированные контейнеры (systemd как PID 1). Порты 80, 443 и 27998 на машине должны быть свободны: контейнер работает в сети хоста. `REHEARSE_BASE_IMAGE` подставляет другой исходный образ вместо `ubuntu:24.04`, например подготовленный для сети за прокси.

## Если что-то не так

| Симптом | Что проверить |
|---|---|
| Браузер ругается на сертификат, или https не открывается | `dig +short <домен>` указывает на VPS; порты 80 и 443 открыты (файрвол, панель провайдера); `journalctl -u caddy -n 50` |
| Страница открылась, но «Переподключение…» не проходит | `systemctl status territory`; `deploy/check.sh <домен>` |
| Выкладка остановилась на сборке | Сообщение компилятора или тестов выше в выводе; при нехватке памяти — swap (`swapon --show`) |
| «the server did not come up» после выкладки | `journalctl -u territory -n 50`, затем `deploy/deploy.sh rollback` |
| Игроки жалуются на задержку | Пинг в правом верхнем углу HUD; метрики `tick_us.p99` (см. раздел 6); регион VPS |
| Игроки часто переподключаются | Почему закрывались соединения: `journalctl -u territory -o cat \| grep "closed:"`. Код 4900 — клиент 6 с не слышал сервер (сеть игрока или VPS), 1001 — вкладку закрыли или перезагрузили; остальные коды — в [server/README.md](../server/README.md#logs--metrics) |
